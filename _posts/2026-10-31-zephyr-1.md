## Introduction
最近、組み込みソフトウェア開発で話題の**Zephyr**を触ってみる。<br>
Zephyrはオープンソースの組み込み向けRTOSで、スレッドやセマフォといったカーネルだけでなく、ドライバ、Bluetooth、ネットワークのスタックもまとめて提供する。<br>
Nordicの無線製品のSDKはZephyrベースであり、TIやNXP、STなどのチップベンダーもZephyr対応を進めている。<br><br>

従来のチップベンダー提供のSDKとZephyrの違いは以下の通り。<br>

| | ベンダーSDK（e.g. TIのSimpleLink SDK） | Zephyr |
|-|-|-|
| 対応チップ | そのベンダーのチップだけ | 複数ベンダーのチップ・ボード |
| ハードの設定 | GUIツール（SysConfigなど）でコード生成 | Devicetreeで記述 |
| 機能の選択 | プロジェクト設定・ライブラリ追加 | Kconfig（`prj.conf`） |
| ドライバAPI | ベンダーごとに違う | 共通API（ボードを変えてもアプリはほぼそのまま） |
| 開発環境 | ベンダーのIDE | west + CMake + GCC（VS Code拡張あり） |

<br>
つまり、「ボードを変えてもアプリのコードをほぼ変えずに済む」という組み込みソフトの抽象化・移植性の高さがZephyrの魅力である。<br><br>

この記事では、[Zephyr RTOS Cookbook](https://www.oreilly.com/library/view/zephyr-rtos-cookbook/9781807429171/)の第1章をベースに、TIの**CC2340R53**（BLE向けのArm Cortex-M0+マイコン）でHello World!を実行する。<br>
書籍はNXPやSTのボードが前提なので、本記事ではCC2340での開発方法を示す。<br><br>

## 1. Zephyrとは
組み込みRTOSの定番であるFreeRTOSがカーネル中心のソフトウェアであるのに対して、Zephyrは**カーネル + ドライバ + サブシステム + ボード定義 + ビルドシステム**がひとまとまりになった組み込み向けプラットフォームである。<br>
FreeRTOSはドライバ・通信スタックを含まないので、ベンダーSDKと組み合わせて開発する必要があった。<br>
一方、Zephyrはそれらの機能が共通APIで抽象化されており、デバイスの違いを意識することなくアプリケーションを開発できる。<br><br>

### 1.1. Zephyrの構成
Zephyr本体のソースコードは、GitHubの[`zephyrproject-rtos/zephyr`](https://github.com/zephyrproject-rtos/zephyr)で公開されている。3.3節で`west update`を実行すると、この記事のワークスペースでは`C:\zephyr-ws\deps\zephyr`に取得される。<br>
そのフォルダ構成は以下の通り。<br>

| ディレクトリ | 中身 |
|-|-|
| `arch/` | CPUアーキテクチャ依存部（Arm、RISC-Vなど） |
| `kernel/` | RTOSカーネル本体（スレッド、スケジューラ、セマフォなど） |
| `drivers/` | GPIO、UART、ADC、SPIなどのドライバ |
| `subsys/` | ログ、シェル、Bluetooth、ネットワークなどの上位機能 |
| `soc/`、`boards/`、`dts/` | チップとボードの定義 |
| `samples/`、`tests/` | サンプルアプリとテスト |

<br>
さらに、チップベンダーの低レベルコード（HAL）やCMSISは**モジュール**として別リポジトリになっている。CC2340なら`hal_ti`が必要となる。<br>
上の表は`zephyr/`フォルダの中身で、モジュールはその外側の`modules/`以下に置かれる。この記事で作るワークスペース（`C:\zephyr-ws`）だと、次のような配置になる。<br>

```text
deps/
|-- zephyr
`-- modules
    |-- hal
    |   |-- ti
    |   |-- cmsis
    |   `-- cmsis_6
    `-- lib
        `-- picolibc
```
`hal/ti`がTIのHAL（`hal_ti`）。Zephyr本体のドライバ（たとえば`zephyr/drivers/serial/uart_cc23x0.c`）が、`#include <driverlib/uart.h>`でこのHALを呼び出している。<br>
つまり、アプリ → Zephyrのドライバ（`drivers/`）→ ベンダーのHAL（`modules/hal/ti`）→ レジスタ、という階層になる。<br><br>

### 1.2. 開発の流れ
Zephyrのビルドでは、westがCMakeを起動し、CMakeがDevicetree、Kconfigの順に処理して、最後にNinjaがGCCを呼び出して実行ファイル`zephyr.elf`を作る。流れは次のとおり。<br>

<img src="/img/1031_3.png" width="100%" height="auto"><br>

1. **west**: Zephyr本体とモジュールを取得（`west update`）し、ビルドや書き込みのコマンドを実行する
1. **CMake**: ビルド構成を生成し、DevicetreeとKconfigの処理を呼び出す
1. **Devicetree**: ハードウェア構成を決める（入力はボードの`.dts`とアプリの`*.overlay`。出力は`zephyr.dts`、`devicetree_generated.h`、Kconfig用の`Kconfig.dts`）
1. **Kconfig**: ソフトウェア機能の有効・無効を決める（入力はボードの`defconfig`、アプリの`prj.conf`、Devicetreeの出力`Kconfig.dts`。出力は`.config`と`autoconf.h`）
1. **Ninja + GCC（Zephyr SDK）**: 生成されたヘッダをインクルードして、コンパイル・リンクする
1. **書き込みツール**: できた`zephyr.elf` / `zephyr.hex`をマイコンへ書き込む

<br>
ポイントは「**設定はすべてコンパイル前に決まる**」こと。KconfigもDevicetreeも最後はCのヘッダ（マクロ）になって、ソースコードにインクルードされる。実行中にハード構成を読みにいくことはない。<br>
CCS（TIの統合開発環境）のSysConfigがやっていることが、ハード側はDevicetree、機能選択はKconfigに分けられている。<br>
Devicetreeには、ピン番号やボード上のLEDのピン、ペリフェラルを使うかどうか（`status = "okay"`）、通信速度といった**ハードウェアの構成**を書く。<br>
Kconfigには、シリアルやログなどのドライバ・サブシステム、カーネル機能のオン・オフとパラメータといった**ソフトウェアの機能**を書く。<br><br>
また、初期化コードは生成されず、ドライバが起動時に勝手に初期化してくれる。<br><br>

## 2. Requirements
- Hardware
    - [LP-EM-CC2340R53](https://www.ti.com/tool/ja-jp/LP-EM-CC2340R53): Texas InstrumentsのBLEマイコンCC2340R53の評価ボード
    - [LP-XDS110ET](https://www.ti.com/tool/LP-XDS110ET): デバッガ（LP-EMボードにはデバッガが載っていないので必須）
- Environment
    - Windows 11
- Software
    - Zephyr v4.4.2
    - Zephyr SDK 1.0.1
    - VS Code + Workbench for Zephyr（拡張機能）
    - [UniFlash](https://www.ti.com/tool/UNIFLASH): TIの書き込み用ツール
    - Tera Term: シリアルモニタ<br><br>

Zephyr公式リポジトリ（v4.4.2）にはR53用のボード定義がないので、R5用の`lp_em_cc2340r5`をそのまま使ってビルドする。<br>
CC2340R5とR53の主な違いは**SRAMの容量**で、R5が36 KB、R53が64 KBである。周辺機能は同じなので、R5用の定義でも動く。<br>

また、ボード定義`lp_em_cc2340r5`の`board.cmake`では、書き込みツール（runner）に**J-Linkしか登録されていない**。つまり、`west flash`やWorkbenchの**Flash/Run**で書き込めるのはJ-Linkだけである。<br>
今回はXDS110（TIのデバッガ）を使うので、ビルドだけZephyrで行い、生成した実行ファイル`zephyr.hex`をUniFlashでボードへ書き込む。<br><br>

## 3. 開発環境の構築
最初の導入だけPowerShell（CLI）で行い、以降の作業はVS Codeで行う。<br><br>

### 3.1. ホストツールのインストール
```powershell
winget install Kitware.CMake Ninja-build.Ninja oss-winget.gperf Python.Python.3.12 Git.Git oss-winget.dtc wget 7zip.7zip
```
コピペするときに1行が途中で改行されると、後半が別コマンド扱いになって失敗する。<br>
また、7-ZipはPATHを通してくれない。Windows版のZephyr SDKは`.7z`で配られるので、自分でユーザー環境変数に追加しておく。<br>
```powershell
[Environment]::SetEnvironmentVariable('Path', [Environment]::GetEnvironmentVariable('Path','User') + ';C:\Program Files\7-Zip', 'User')
```
PowerShellは起動時にしかPATHを読まないので、インストール後はPowerShellを開き直すこと。<br><br>

### 3.2. ワークスペースとPython仮想環境
```powershell
mkdir C:\zephyr-ws\my_app -Force; cd C:\zephyr-ws
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install west
```
作業フォルダは**日本語やスペースを含まない短いパス**にする。Windowsのパス長制限（260文字）に引っかかると、コンパイル中に謎のエラーが出る。<br>
westはこのvenvの中にしか入っていないので、PowerShellを開くたびに`Activate.ps1`で入り直す必要がある。<br><br>

### 3.3. west.ymlでZephyrを取得
書籍では`west init --mr v4.4.1`でZephyrの全モジュールを取得しているが、本記事ではCC2340に必要なモジュールだけ取得するために、アプリ側にマニフェスト（`west.yml`）を置いた。この`west.yml`で取得した`deps`フォルダ（`C:\zephyr-ws\deps`）は約1.7 GBだった。全モジュールを取得した場合の容量は計測していない。<br>
```yaml
manifest:
  remotes:
    - name: zephyrproject
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject
      revision: v4.4.2
      import:
        path-prefix: deps
        name-allowlist:
          - cmsis
          - cmsis_6
          - hal_ti
          - picolibc
  self:
    path: my_app
```
{: data-file="my_app/west.yml"}

<br>
```powershell
west init -l my_app
west update
```
`west list`で、`zephyr`が`deps/zephyr`に置かれていればOK。<br>
`zephyr`の項目に`path: deps/zephyr`を足してしまうと、`path-prefix`と二重になって`deps\deps\zephyr`に置かれる。これで失敗した。<br><br>

### 3.4. Pythonパッケージと Zephyr SDK
```powershell
cd C:\zephyr-ws\deps\zephyr; west packages pip --install
west sdk install -t arm-zephyr-eabi
```
CC2340はArmなので、`arm-zephyr-eabi`だけ入れれば十分。<br>
`west packages pip --install`と`west sdk install`は、どちらもPythonの仮想環境（venv）を有効にした状態で実行する。有効になっていると、PowerShellのプロンプトの先頭に`(.venv)`が付く。<br>
`west sdk install`でZephyr SDKを入れる場所は、`-d`と`-b`を指定しなければ`C:\Users\<ユーザー名>\zephyr-sdk-1.0.1`になる。`-t arm-zephyr-eabi`でArm用ツールチェーンだけを入れても約1.6 GBあるので、Cドライブの空き容量に注意。<br>
ちなみに`west packages`はwest本体ではなくZephyr本体が提供する拡張コマンドなので、Zephyrの取得に失敗していると`unknown command "packages"`と怒られる。<br><br>

### 3.5. VS CodeにWorkbench for Zephyrを追加
VS Codeへ拡張機能「Workbench for Zephyr」を入れて、初期設定を行う。<br>
1. **Host Tools Manager** → **Verify host tools**（Workbench専用のツール一式を確認）
1. VS Codeで`C:\zephyr-ws`を開くと、West Workspacesに自動で表示される
1. Toolchainsの +（Add Toolchain）→ Source: **Local** で`%USERPROFILE%\zephyr-sdk-1.0.1`を登録

<br>

3つ目は、自動でパス設定されるらしいが、私の環境では出てこなかった。Sourceを**Official**のままにすると、SDKをもう一度ダウンロードしてしまうので注意。<br><br>

## 4. Hello World!のアプリケーション作成
### 4.1. アプリの作成とビルド
WorkbenchのエクスプローラタブのApplicationsの横の+ボタンを押して、**Add Application**画面で以下の項目を選択→**Create**を押すと、サンプルの`hello_world`を元に新規のアプリが作られる。<br>


| 項目 |  |
|-|-|
| west workspace | `C:\zephyr-ws` |
| Toolchain | `Zephyr SDK 1.0.1` |
| Board | `lp_em_cc2340r5` |
| Sample project | `hello_world` |

<img src="/img/1031_2.png" width="90%" height="auto"><br><br>

**Add Application**で作ったアプリ`hello_world`は、`C:\zephyr-ws\applications\hello_world`に置かれる。書籍の構成と同じく、Zephyr本体の`deps`フォルダとは別のフォルダである。<br>
Workbenchでビルドすると、`C:\zephyr-ws\applications\hello_world\build\primary\zephyr\`に`zephyr.elf`と`zephyr.hex`が出力される。<br>

アプリを右クリック → **Build**を押すと、ビルドが実行される。ログの最後にメモリ使用量が出れば成功。<br>

```text
Memory region         Used Size  Region Size  %age Used
           FLASH:       13964 B       512 KB      2.66%
             RAM:        4216 B        36 KB     11.44%
```
ログの前半には、どの設定ファイルが使われたかが出ている。`Ctrl+F`で探すとデバッグの際に参考になる。<br>
- `Found BOARD.dts: …\lp_em_cc2340r5.dts`: ボードのDevicetree
- `Loaded configuration …\lp_em_cc2340r5_defconfig`: ボードの既定のKconfig
- `Merged configuration …\hello_world\prj.conf`: `hello_world`アプリのKconfig。Workbenchが自動で書き込んだデバッグ用の設定だけが入っている

<br>

ビルドの際に`there is no registered task type 'zephyr-workbench-shell'`というエラーが出たら、`Ctrl+Shift+P` → **Developer: Reload Window**で拡張機能を再起動すれば直った。<br><br>

### 4.2. 書き込みと実行
UniFlashを開いて、Deviceで**CC2340R5**、Connectionで**Texas Instruments XDS110 USB Debug Probe**を選択する。<br>
`C:\zephyr-ws\applications\hello_world\build\primary\zephyr\zephyr.hex`を**Load Image**で書き込む。<br>

Tera Termで「XDS110 Class Application/User UART」のCOMポートを115200bps / 8N1 / フロー制御なしで開き、XDS110のリセットボタンを押すと<br>

<img src="/img/1031_1.png" width="80%" height="auto"><br>

Hello World!が表示された。<br>

1行目はZephyrカーネルが起動時に出すブートバナー、2行目が`main.c:11`の`printf()`の出力になる。<br>
```c
#include <stdio.h>

int main(void)
{
	printf("Hello World! %s\n", CONFIG_BOARD_TARGET);

	return 0;
}
```
{: data-file="hello_world/src/main.c"}
<br>
`CONFIG_BOARD_TARGET`はKconfigが作るマクロで、ビルド時に選んだボード名（`lp_em_cc2340r5/cc2340r5`）が文字列として埋め込まれている。<br><br>

#### 4.2.1. printf()がシリアルモニタに表示される仕組み
`main.c`にはUARTについて何も書かれていない。出力先を決めているのは、ビルドフォルダ（`build\primary\zephyr\`）にできる2つのファイルだ。<br>

| ファイル | 概要 | 内容 |
|-|-|-|
| `zephyr.dts` | Devicetreeの最終結果 | `zephyr,console = &uart0;` と、`uart0`の`current-speed = <115200>;` |
| `.config` | Kconfigの最終結果 | `CONFIG_SERIAL=y`、`CONFIG_CONSOLE=y`、`CONFIG_UART_CONSOLE=y` |

<br>
つまり、「コンソールはUART0、速度は115200bps」というハードの設定はボードのDevicetreeが、「UARTドライバとコンソールを入れる」というソフトの話はボードの`defconfig`（Kconfig）で決めている。<br>

LP-EM-CC2340R53のUART0のピン（TX: DIO20、RX: DIO22）はボードのDevicetree（pinctrl）で定義されている。UART0の各ピンはXDS110を通してPCへつながっているので、printf()の文がUARTで送信されて、Tera Term上で表示される。<br>
ボードを変えれば、この2つのファイルの中身が変わるだけで、`main.c`はそのまま。これが「ボードを変えてもアプリはそのまま」という、Zephyrの移植性の高さだ。<br><br>

## Summary
CC2340R53でZephyrのHello World!を行った。<br>
ツールや設定ファイルが多いので、結構めんどくさそう。GUIのコンフィギュレーションツールが使えないのも不便。<br>
また、Zephyr公式リポジトリv4.4.2（`zephyrproject-rtos/zephyr`）ではボード定義`lp_em_cc2340r5`の`lp_em_cc2340r5.yaml`で定義されている機能は`gpio`と`uart`だけだった。<br>
一方、Zephyr公式リポジトリをベースにTIが[TexasInstruments/simplelink-zephyr](https://github.com/TexasInstruments/simplelink-zephyr)を公開しており、様々なペリフェラルに対応している。今後BLEを使う際は、`simplelink-zephyr`を試してみたい。<br>
次回は、[ソフトウェアの構成を決めるKconfigの仕組み](https://h4rutank.github.io/electronics/2026/11/02/zephyr-2.html)を学ぶ。<br>
