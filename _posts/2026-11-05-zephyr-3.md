## 1. Devicetreeとは
Devicetreeは、ボードのハードウェアをツリー構造のテキスト（**DTS**）で記述する仕組みである（参考: [Devicetree](https://docs.zephyrproject.org/4.4.2/build/dts/index.html)）。<br>
- **ノード**（UART、ADC、LEDなど、1つのハードウェアに対応するもの）とその**プロパティ**（アドレス、ピン、通信速度などの設定値）を記述する
- Devicetreeの出力は、`zephyr.dts`と`devicetree_generated.h`の2種類

<br><br>

KconfigとDevicetreeの使い分けは、[Zephyr入門 (2)](https://h4rutank.github.io/electronics/2026/11/02/zephyr-2.html)の第1節の表を参照してほしい。<br>
**Devicetreeはハードウェアとその起動時の設定を書いて、Kconfigはビルドに入れるソフトウェアの機能を決める**。<br><br>

個人的に、組み込みLinuxのDevicetreeの書き方とほぼ同じだと感じている。<br>
比較すると、以下の表のようになる。<br>

| 項目 | Linuxカーネル | Zephyr |
|-|-|-|
| 記述形式 | `.dts`、`.dtsi`（DTS形式） | 同じDTS形式。`dtc`は検査にだけ使い、出力は使わない |
| SoCとボードの分担 | SoCの`.dtsi`を、ボードの`.dts`が取り込んで、ノードを書き換える | 同じ。SoCは`dts\arm\ti\cc23x0.dtsi`、ボードは`boards\ti\lp_em_cc2340r5\lp_em_cc2340r5.dts` |
| ドライバとの結び付け | ノードの`compatible`の文字列で、担当ドライバが決まる | 同じ。ドライバ側の`DT_DRV_COMPAT`と結び付く |
| 有効・無効 | `status = "okay"`、`"disabled"` | 同じ |
| 特別なノード | `/chosen`、`/aliases` | `/chosen`（`zephyr,console`など）、`/aliases` |
| bindingの書式 | YAML（dt-schema） | 独自のYAML（dt-schemaは使わない） |
| 実行時の扱い | ブートローダがバイナリ（dtb）を渡し、起動時に読む | ビルド時にCのマクロに変換する。実行時には存在しない |

<br><br>

### 1.1. 開発の流れ
Devicetreeを使うと、ボードごとのハードウェアの違いを、**ソースコードにアドレスやピン番号を書かずに**コンフィグファイル側にまとめられる。<br>
たとえば、LEDのピンやADCのチャネルをDevicetreeに書いておき、コードでは`led0`のような名前で参照する。<br><br>

開発手順は以下の通り。<br>
この記事では、手順1～3をCC2340R5上でADCの動作を例に確かめる。<br>
手順4は、自作ノード`toto-led`を試す。<br>

| 手順 | やること | 参照先 | 節 |
|-|-|-|-|
| 1 | ボードのDevicetreeを読み、使えるノード・alias・ピンを調べる | `zephyr.dts` | 2.1 |
| 2 | アプリ用のDevicetree追加ファイル`.overlay`を作成 | `boards\lp_em_cc2340r5.overlay` | 2.2 |
| 3 | Cのコードで、ノードの値を読み、デバイスを使う | `DT_ALIAS()`、`DT_PROP()`、`DEVICE_DT_GET()` | 2.3 |
| 4 | 必要なら、自分専用のbindingとノードを作る | `dts\bindings`のYAML、`.overlay` | 2.4 |

<br><br>

### 1.2. デバッグでの調べ方
設定したつもりなのに、ビルドが通らなかったり、ハードウェアが動かなかったりすることがある。そのときは、以下のように調べていく。<br>
ビルドのログ出力・生成物から原因の候補を絞っていくことができる。<br>

| 手順 | 調べること | 参照先 | 節 |
|-|-|-|-|
| 1 | ビルドが成功したか。`devicetree error`が出ていないか | ビルドログ | 3.1 |
| 2 | `.overlay`が読み込まれたか | ビルドログの`Found devicetree overlay`の行 | 2.2 |
| 3 | ノードの値が、最終的にどうなったか。どのファイルの何行目が決めたか | `zephyr.dts`の行末のコメント | 2.1 |
| 4 | Cのマクロが作られているか | `devicetree_generated.h` | 2.3、3.1 |
| 5 | ドライバの場合、ノードが`okay`で、ドライバが有効になっているか | `zephyr.dts`の`status`、`.config` | 3.2 |

<br><br>

## 2. Devicetree開発手順
1.1節の4つの手順を、順に説明する。<br>

### 2.1. ボードのDevicetreeを読む
ビルドすると、ボードの`.dts`、SoCの`.dtsi`、アプリの`.overlay`が1つにまとまり、`zephyr.dts`ができる（参考: [Input and output files](https://docs.zephyrproject.org/4.4.2/build/dts/intro-input-output.html)）。<br>
`zephyr.dts`には、各プロパティが**どのファイルの何行目から来たか**が、行末のコメントに書かれている。<br>
そのため、`zephyr.dts`を読めば、使えるノードの名前、ピンの割り当て、alias、その値を決めたファイルが分かる。<br><br>

#### 1) ノードの文法
まず、ノードの文法を確認する（参考: [Syntax and structure](https://docs.zephyrproject.org/4.4.2/build/dts/intro-syntax-structure.html)）。UARTのノードは、次のように書く。<br>

```dts
uart0: uart@40034000 {
	compatible = "ti,cc23x0-uart";
	reg = <0x40034000 0x52>;
	status = "okay";
	current-speed = <115200>;
};
```

- `uart0:`は**ノードラベル**で、別の場所から`&uart0`で参照するための名前である
- `uart@40034000`はノード名で、`@`の後ろは**ユニットアドレス**である。メモリマップドのペリフェラルでは、レジスタ領域の先頭アドレスになる。`reg`の最初の値（`0x40034000`）と、同じ値にする
- `{ }`の中が**プロパティ**で、`名前 = 値;`の形で書く

プロパティの文法は以下の通り。<br>

| プロパティ | 意味 |
|-|-|
| `compatible` | ノードが表すハードウェアの名前。`"vendor,device"`の形が推奨。ビルドシステムがbindingを探す手がかりで、ドライバが担当ノードを探す手がかりでもある |
| `reg` | レジスタ領域の先頭アドレスと、バイト数 |
| `status` | `"okay"`か`"disabled"`。`status`が書かれていないノードも、有効として扱われる。有効でないと、ドライバの`struct device`が作られない |
| `interrupts` | 割り込みの指定 |

<br><br>

また、UARTの先頭アドレス`0x40034000`は、TIのテクニカルリファレンスマニュアル（[SWCU193A](https://www.ti.com/lit/ug/swcu193/swcu193.pdf)）の第3.1節Memory MapのTable 3-1にある、UART0のベースアドレスと一致する。<br><br>

#### 2) zephyr.dtsを読む
`hello_world`をビルドしたあと、`C:\zephyr-ws\applications\hello_world\build\primary\zephyr\zephyr.dts`を、VS Codeで開く。<br>
`uart0:`を検索すると、次のように、行末のコメントに、値の参照先が書かれている。<br>

```dts
uart0: uart@40034000 {
	compatible = "ti,cc23x0-uart";   /* in deps\zephyr\dts\arm\ti\cc23x0.dtsi:101 */
	reg = < 0x40034000 0x52 >;       /* in deps\zephyr\dts\arm\ti\cc23x0.dtsi:102 */
	status = "okay";                 /* in deps\zephyr\boards\ti\lp_em_cc2340r5\lp_em_cc2340r5.dts:93 */
	current-speed = < 0x1c200 >;     /* in deps\zephyr\boards\ti\lp_em_cc2340r5\lp_em_cc2340r5.dts:94 */
	pinctrl-0 = < &uart0_rx_default &uart0_tx_default >;
};
```
{: data-file="hello_world/build/primary/zephyr/zephyr.dts（一部を省略）"}

この結果から、次のことが分かる。<br>

| 行 | 分かること |
|-|-|
| `compatible`、`reg` | SoCの`.dtsi`（`dts\arm\ti\cc23x0.dtsi`）が決めている |
| `status = "okay"` | SoC側では`disabled`だったものを、ボードの`.dts`が`okay`に書き換えている |
| `current-speed`（値は`0x1c200`） | `0x1c200`は10進数で115200。Tera Termのボーレートの設定は、ここが根拠になっている |

つまり、Devicetreeは、SoC、ボード、アプリの`.overlay`の順に重なり、**後のものが、前の値を書き換える**。<br><br>

#### 3) aliasからLED、ボタンのコンフィギュレーションを調べる
次に、`zephyr.dts`で`aliases {`を検索する。<br>
`aliases`は、アプリが使う「あだ名」である。<br>
ボードごとに違うノードを、同じあだ名で指定できるので、アプリは`led0`だけを使えば、別のボードでも、そのボードのLEDが光る。<br>

```dts
aliases {
	led0 = &led0;
	led1 = &led1;
	sw0 = &btn0;
	sw1 = &btn1;
};
```
{: data-file="hello_world/build/primary/zephyr/zephyr.dts（一部を省略）"}

同じく`zephyr.dts`で`led0:`と`btn0:`を検索すると、次のようなGPIOの設定が見つかる。<br>

```dts
gpios = < &gpio0 0xf 0x0 >;    /* led0。緑LED */
gpios = < &gpio0 0xa 0x11 >;   /* btn0。BTN-1 */
```
{: data-file="hello_world/build/primary/zephyr/zephyr.dts（一部を省略）"}

`gpios`は3つの値の組み合わせで、`&gpio0`がGPIOコントローラ（phandle）、2つ目がピン番号、3つ目がフラグを意味する。<br>
`led0`は、GPIO0の15番ピン（DIO15）で、`0x0`は、フラグなし（active high）である。<br>
`btn0`は、GPIO0の10番ピン（DIO10）で、`0x11`は、`GPIO_ACTIVE_LOW`と`GPIO_PULL_UP`を合わせたフラグである。<br><br>

#### 4) ADCのピンを調べる
最後に、ADCのピンを調べる。<br>
まず、`zephyr.dts`で`adc0:`を検索すると、次のノードが見つかる。<br>

```dts
adc0: adc@40050000 {
	compatible = "ti,cc23x0-adc";
	status = "okay";                 /* in deps\zephyr\boards\ti\lp_em_cc2340r5\lp_em_cc2340r5.dts:121 */
	pinctrl-0 = < &adc0_ch0 &adc0_ch2 &adc0_ch3 &adc0_ch4 &adc0_ch6 &adc0_ch8 >;
	pinctrl-names = "default";
};
```
{: data-file="hello_world/build/primary/zephyr/zephyr.dts（一部を省略）"}

ボードの`.dts`が、`status = "okay"`にして、`pinctrl-0`で、6本のピンをADCの入力に割り当てていることが分かる。<br>
`&adc0_ch2`などは、ピンの設定を書いたノードの名前である。<br><br>

2つ目は、そのノードが書かれた、ボード定義のファイル`C:\zephyr-ws\deps\zephyr\boards\ti\lp_em_cc2340r5\lp_em_cc2340r5-pinctrl.dtsi`である（[GitHub](https://github.com/zephyrproject-rtos/zephyr/blob/v4.4.2/boards/ti/lp_em_cc2340r5/lp_em_cc2340r5-pinctrl.dtsi)）。<br>
VS Codeでこのファイルを開き、`adc0_ch2:`を検索すると、`pinmux = <5 DIO5_ADC2>;`が見つかる。ピン5（DIO5）が、ADCのチャネル2であることを示している。<br>
同じように、6つのノードを調べると、次の対応になる。<br>

| ADCチャネル | 0 | 2 | 3 | 4 | 6 | 8 |
|-|-|-|-|-|-|-|
| ピン | DIO7 | DIO5 | DIO2 | DIO1 | DIO25 | DIO23 |

ただし、この時点では、「どのチャネルを、どう測るか」を書いたノードがない。つまり、
ボードの`.dts`は「ADCを有効にして、ピンを配線する」ところまでで、「どのチャネルをどんな条件で読むか」を定義していない。<br>
それを`.overlay`で足す。<br><br>

### 2.2. .overlayで、ボードのDevicetreeに追記・上書きする
`.overlay`は、Zephyr本体やボード定義のファイルを書き換えずに、アプリごとのハードウェア設定をボードのDevicetreeへ追加するファイルである（参考: [Input and output files](https://docs.zephyrproject.org/4.4.2/build/dts/intro-input-output.html)）。<br>
アプリのフォルダ直下に作成して、`.dts`と同じくノードやプロパティを記述する。<br><br>

「どのチャネルを、どんな条件で読むか」は接続するセンサ次第なので、アプリごとに異なる。<br>
そのため、ADCのチャネル設定は`.overlay`で追加する必要がある。<br><br>

ここでは、DIO5（ADCチャネル2）に可変抵抗をつないでアナログ電圧を読む。<br>
可変抵抗の両端を3.3 VとGNDに、中央の端子をDIO5につなぐ。<br>
`my_adc`というアプリを、[Zephyr入門 (1)](https://h4rutank.github.io/electronics/2026/10/31/zephyr-1.html)の4.1節と同じ手順で作り、`boards`フォルダに、`lp_em_cc2340r5.overlay`を作成する。ファイル名はボード名と完全に一致させる。<br>

```dts
#include <zephyr/dt-bindings/adc/adc.h>

/ {
	aliases {
		myadc = &adc0;
	};
};

&adc0 {
	#address-cells = <1>;
	#size-cells = <0>;

	channel@2 {
		reg = <2>;
		zephyr,gain = "ADC_GAIN_1";
		zephyr,reference = "ADC_REF_VDD_1";
		zephyr,vref-mv = <3300>;
		zephyr,acquisition-time = <ADC_ACQ_TIME_DEFAULT>;
		zephyr,resolution = <12>;
	};
};
```
{: data-file="my_adc/boards/lp_em_cc2340r5.overlay"}

この`.overlay`は、次のことをしている。<br>

| 部分 | 意味 |
|-|-|
| `/ { aliases { myadc = &adc0; }; };` | ルートノードに、alias`myadc`を足す。Cのコードで、`adc0`を、この名前で指す |
| `&adc0 { ... };` | ボードの`.dts`にある`adc0`ノードに、追記する。ルートから書き直す必要はない |
| `#address-cells`、`#size-cells` | 子ノードの`reg`が、「番号1個、サイズなし」であることを示す決まり文句 |
| `channel@2`、`reg`（値は2） | ADCのチャネル2。`@`の後ろの数字と、`reg`の値は、一致させる |
| `zephyr,gain`、`zephyr,reference`、`zephyr,resolution` | 増幅率、基準電圧、分解能。CC2340R5のドライバ（`adc_cc23x0.c`）が受け付けるのは、gainが`ADC_GAIN_1`のみ、referenceが`ADC_REF_INTERNAL`、`ADC_REF_EXTERNAL0`、`ADC_REF_VDD_1`の3つ、分解能が8、10、12ビット |
| `zephyr,vref-mv` | 基準電圧の値（mV）。電源電圧を基準にしているので3300 |

**Build**すると、ビルドログに、次の行が出る。<br>

```text
-- Found devicetree overlay: .../my_adc/boards/lp_em_cc2340r5.overlay
```

`build\primary\zephyr\zephyr.dts`を開くと、`adc0`の中に`channel@2`が増え、`aliases`に`myadc = &adc0;`が増えている。<br>
行末のコメントには、`.overlay`のファイル名と行番号が出る。<br>
`.overlay`は、`boards\ボード名.overlay`があれば、それが自動で使われる。なければ、アプリ直下の`ボード名.overlay`、`app.overlay`の順に探される（[`configuration_files.cmake`](https://github.com/zephyrproject-rtos/zephyr/blob/v4.4.2/cmake/modules/configuration_files.cmake)）。<br><br>

### 2.3. Cのコードで使う
Devicetreeは、実行時には存在せず、ビルド時に、`devicetree_generated.h`のマクロになる。<br>
そのため、Cのコードでは、`DT_...`というマクロで、ノードを指して、値を読む（参考: [Devicetree access from C/C++](https://docs.zephyrproject.org/4.4.2/build/dts/api-usage.html)）。<br><br>

#### 1) ノードを指すマクロ
ノードを指すマクロの値を、**ノード識別子**という。ノード識別子は変数に入れられない。<br>

| 取り方 | マクロの例 |
|-|-|
| ノードラベル | `DT_NODELABEL(adc0)` |
| alias | `DT_ALIAS(myadc)` |
| 子ノード | `DT_CHILD(node, channel_2)` |
| `/chosen`のプロパティ | `DT_CHOSEN(zephyr_console)` |

DTSの名前は、**英数字以外（`-`、`@`、`,`など）を`_`に、英字を小文字に**して、マクロに書く。<br>
たとえば、`channel@2`は`channel_2`、プロパティ`zephyr,vref-mv`は`zephyr_vref_mv`になる。<br>
値は、`DT_PROP(ノード識別子, プロパティ名)`で読む。<br>
`DT_PROP_OR(ノード識別子, プロパティ名, 既定値)`は、プロパティがなければ、既定値になる。<br>
`DT_NODE_HAS_STATUS(ノード識別子, okay)`は、ノードの`status`が`okay`かを調べる。<br>
`devicetree_generated.h`には、これらのマクロの実体が並ぶ。`my_adc`のビルドには、次の行があった。<br>

```c
#define DT_N_S_soc_S_adc_40050000_S_channel_2_P_zephyr_vref_mv 3300
```

これは、「ノード`/soc/adc@40050000/channel@2`のプロパティ`zephyr,vref-mv`は3300」という意味である。<br>
`DT_PROP(...)`は、最終的に、このマクロに展開される。<br><br>

#### 2) ADCを読む
ADCのドライバを有効にするために、[Zephyr入門 (2)](https://h4rutank.github.io/electronics/2026/11/02/zephyr-2.html)の3.2節の通り、`prj.conf`に追記する。<br>

```text
CONFIG_ADC=y
```
{: data-file="my_adc/prj.conf"}

`src\main.c`を以下のように書き換える。<br>

```c
#include <inttypes.h>
#include <zephyr/kernel.h>
#include <zephyr/drivers/adc.h>

#define MY_ADC_NODE    DT_ALIAS(myadc)
#define MY_ADC_CH_NODE DT_CHILD(MY_ADC_NODE, channel_2)
#define ADC_VREF_MV    DT_PROP(MY_ADC_CH_NODE, zephyr_vref_mv)
#define ADC_RESOLUTION DT_PROP_OR(MY_ADC_CH_NODE, zephyr_resolution, 12)
#define ADC_ENABLED    DT_NODE_HAS_STATUS(MY_ADC_NODE, okay)

static const struct device *adc = DEVICE_DT_GET(MY_ADC_NODE);
static const struct adc_channel_cfg ch_cfg = ADC_CHANNEL_CFG_DT(MY_ADC_CH_NODE);

int main(void)
{
	int err;
	uint16_t buf;
	struct adc_sequence sequence = {
		.channels = BIT(ch_cfg.channel_id),
		.buffer = &buf,
		.buffer_size = sizeof(buf),
		.resolution = ADC_RESOLUTION,
	};

	printk("ADC vref: %d mV\n", ADC_VREF_MV);
	printk("ADC resolution: %d bits\n", ADC_RESOLUTION);
	printk("ADC enabled? %s\n", ADC_ENABLED ? "yes" : "no");

	if (!device_is_ready(adc)) {
		printk("ADC device not ready\n");
		return 0;
	}

	err = adc_channel_setup(adc, &ch_cfg);
	if (err < 0) {
		printk("Could not setup ADC channel (%d)\n", err);
		return 0;
	}

	while (1) {
		int32_t val_mv;

		err = adc_read(adc, &sequence);
		if (err < 0) {
			printk("Could not read ADC (%d)\n", err);
			k_sleep(K_MSEC(1000));
			continue;
		}

		val_mv = buf;
		printk("ADC raw: %" PRId32, val_mv);
		err = adc_raw_to_millivolts(ADC_VREF_MV, ch_cfg.gain, sequence.resolution, &val_mv);
		if (err < 0) {
			printk(" (voltage conversion not available)\n");
		} else {
			printk("  Voltage: %" PRId32 " mV\n", val_mv);
		}
		k_sleep(K_MSEC(1000));
	}
	return 0;
}
```
{: data-file="my_adc/src/main.c"}

コードは、次のことをしている。<br>

| 部分 | 意味 |
|-|-|
| `DEVICE_DT_GET(MY_ADC_NODE)` | ノードに対応するデバイス（`struct device`）を取り出す。ドライバが、起動時に作ったもの |
| `ADC_CHANNEL_CFG_DT(MY_ADC_CH_NODE)` | `channel@2`のプロパティ（gain、reference、チャネル番号など）から、設定の構造体を作る |
| `device_is_ready(adc)` | ドライバの初期化が成功したかを確認する。使う前に、必ず確認する |
| `adc_channel_setup()`、`adc_read()` | チャネルを設定してから、読む |
| `adc_raw_to_millivolts()` | 読んだ値（0〜4095）を、mVに換算する |

`buf`が`uint16_t`なのは、CC2340R5のADCドライバ（`adc_cc23x0.c`）が、サンプルを`uint16_t`で書き込むからである。<br>
**Build**して、UniFlashで書き込み、Tera Termでシリアルモニタを表示する。<br>
すると、1秒ごとにアナログ入力電圧が表示される。可変抵抗を回すと値は変わる。<br>

```text
ADC vref: 3300 mV
ADC resolution: 12 bits
ADC enabled? yes
ADC raw: 2048  Voltage: 1650 mV
```

#### 3) なぜCC2340R5専用の関数が、出てこないのか
コードには、`adc_read()`などの、共通のAPIしか出てこない。それでも、CC2340R5のADCが動くのは、`compatible`がデバイスドライバを結び付けているから。<br><br>

`adc_read()`は、`struct device`の中のドライバ関数表の`read`を呼ぶだけの関数で、CC23x0では、`.read = adc_cc23x0_read`である。<br>
このドライバ（[`drivers/adc/adc_cc23x0.c`](https://github.com/zephyrproject-rtos/zephyr/blob/v4.4.2/drivers/adc/adc_cc23x0.c)）の冒頭で`#define DT_DRV_COMPAT ti_cc23x0_adc`と定義されており、`compatible = "ti,cc23x0-adc"`のノードを担当していることが分かる。<br>
ドライバの中では、TIのdriverlib（`ADCSetInput()`など）とレジスタ定義（`ADC_BASE`など）が呼び出されており、最終的に`DT_INST_FOREACH_STATUS_OKAY(...)`で`status = "okay"`のノードの数だけ`struct device`の実体をつくっている。<br>
つまり、**どのドライバが動くかは、Devicetreeの`compatible`で決まる**。<br><br>

### 2.4. 自分専用のbindingを作る
Zephyr本体にない、自分専用のノードの種類を作ることもできる。<br>
ここでは、「どのLEDを、何ミリ秒間隔で点滅させるか」を、Devicetreeに書くための`toto-led`を作る。<br>
**binding**は、ノードに書けるプロパティの名前と型を決めるYAMLファイルである（参考: [Introduction to Devicetree Bindings](https://docs.zephyrproject.org/4.4.2/build/dts/bindings.html)）。<br>
ビルドシステムは、ノードの`compatible`とbindingの`compatible:`の行が、一致したものを、そのノードのbindingとして使う。<br>
bindingは、ノードの**検証**（必須のプロパティがあるか、型が合っているか）と、`devicetree_generated.h`の**マクロの生成**に使われる。<br><br>

`mytotoled`というアプリを作り、`prj.conf`には、`CONFIG_GPIO=y`だけを書く。<br>
bindingは、アプリの`dts\bindings`フォルダに置く。<br>
`dts\bindings`の下に置いたYAMLだけが読み込まれ、アプリ直下に置いても無視される。<br>

```yaml
description: Example custom node describing a single LED GPIO and a blink delay.

compatible: "toto-led"

properties:
  toto-gpios:
    type: phandle-array
    required: true
    description: My LED GPIO.

  my-delay-ms:
    type: int
    default: 500
    description: Blink delay in milliseconds.
```
{: data-file="mytotoled/dts/bindings/toto-led.yaml"}

このbindingは、次のことを決めている（参考: [Bindings syntax](https://docs.zephyrproject.org/4.4.2/build/dts/bindings-syntax.html)）。<br>

| 部分 | 意味 |
|-|-|
| `compatible: "toto-led"` | このbindingが担当するノードの`compatible` |
| `type` | プロパティの型。`int`、`string`、`array`、`phandle`、`phandle-array`など |
| `required: true` | このプロパティがないノードがあると、ビルドが失敗する。省略すると`false`で、公式ドキュメントは、`required: false`と書くことを非推奨としている |
| `default: 500` | プロパティがないときに、書かれたものとして扱う値。`required: true`とは、同時に使えない |
| `toto-gpios` | GPIOを指すプロパティの名前は、`-gpios`か`-gpio`で終わらせる決まり |

ノードは、アプリの`boards\lp_em_cc2340r5.overlay`に書く。赤LED（DIO14）を、このノードで指定する。<br>

```dts
#include <zephyr/dt-bindings/gpio/gpio.h>

/ {
	toto_led0: toto_led0 {
		compatible = "toto-led";
		toto-gpios = <&gpio0 14 GPIO_ACTIVE_HIGH>;	/* red LED, DIO14 */
		my-delay-ms = <1000>;
	};

	aliases {
		mytotoled = &toto_led0;
	};
};
```
{: data-file="mytotoled/boards/lp_em_cc2340r5.overlay"}

`src\main.c`は、次の内容にする。<br>

```c
#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>

#define TOTO_NODE      DT_ALIAS(mytotoled)
#define BLINK_DELAY_MS DT_PROP(TOTO_NODE, my_delay_ms)

static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(TOTO_NODE, toto_gpios);

int main(void)
{
	int ret;

	if (!gpio_is_ready_dt(&led)) {
		printk("LED GPIO device not ready\n");
		return 0;
	}

	ret = gpio_pin_configure_dt(&led, GPIO_OUTPUT_INACTIVE);
	if (ret != 0) {
		printk("Failed to configure LED: %d\n", ret);
		return 0;
	}

	printk("Blinking with delay %d ms\n", BLINK_DELAY_MS);
	while (1) {
		gpio_pin_toggle_dt(&led);
		k_sleep(K_MSEC(BLINK_DELAY_MS));
	}
	return 0;
}
```
{: data-file="mytotoled/src/main.c"}

`gpio_dt_spec`は、Devicetreeの`gpios`の3つの情報（GPIOコントローラ、ピン番号、フラグ）をまとめた構造体である。<br>
`_dt`が付いた関数に、これを渡すと、フラグも自動で反映される。<br>
たとえば、`GPIO_ACTIVE_LOW`と書かれたノードでは、コードで「押された ＝ active」として扱える。回路の極性を意識する必要がない。<br>
**Build**して、書き込むと、Tera Termに`Blinking with delay 1000 ms`と表示されて、赤LEDが1秒ごとに点滅する。<br>

<img src="/img/1105_2.png" width="80%" height="auto"><br>

`.overlay`の`my-delay-ms`の行を消すと、`devicetree_generated.h`の`DT_N_S_toto_led0_P_my_delay_ms`が、bindingの既定値の`500`になった。<br><br>

## 3. Devicetreeのエラー
### 3.1. ビルドエラー
Devicetreeの誤りは、ビルドが止まるか、ビルドは通っても、リンクやコンパイルで失敗する、という形で出る。<br>

| 症状 | 原因 |
|-|-|
| 構成の生成の段階で、`devicetree error: 'toto-gpios' is marked as required in 'properties:' ...`と出て、ビルドが止まる | bindingで`required: true`にしたプロパティを、ノードに書いていない（`.overlay`の`toto-gpios`の行を消した） |
| `devicetree error: 'other-value' appears in /node_b ..., but is not declared in 'properties:'`と出て、ビルドが止まる | bindingに書いていないプロパティを、ノードに書いた |
| `'DT_N_S_node_a_P_my_value' undeclared`で、コンパイルエラー | `compatible`に対応するbindingがないノードのプロパティを、`DT_PROP`で読んだ |
| `undefined reference to '__device_dts_ord_31'`で、リンクエラー | ノードの`compatible`が、ドライバの`DT_DRV_COMPAT`と一致していない（`&adc0 { compatible = "acme,unknown-adc"; };`と書いた） |

3つ目のエラーのときは、`build\primary\zephyr\include\generated\zephyr\devicetree_generated.h`で、`DT_N_S_ノード_P_プロパティ`の名前を検索する。なければ、bindingが足りない。<br>
マクロの名前は、2.3節の規則で、DTSの名前から作られる。<br><br>

### 3.2. ドライバが有効化されない
ドライバが有効になるには、Devicetreeで、ノードの`status`が`okay`であることと、Kconfigで、ドライバを使うと宣言していること（たとえば`CONFIG_ADC=y`）の、両方が必要である。<br>
Kconfig側の仕組みは、[Zephyr入門 (2)](https://h4rutank.github.io/electronics/2026/11/02/zephyr-2.html)の3.2節で説明した。<br><br>

## Summary
Devicetreeの開発手順とデバッグ方法を学んだ。<br>

- ボードのDevicetreeは、`zephyr.dts`で読む
- ボードの`.dts`が決めるのはハードウェアの有効化とピンの配線までで、「何をどう読むか」はアプリの`boards\ボード名.overlay`に記載
- どのドライバが動くかは、`compatible`で決まる
- 自分専用のノードは、`dts\bindings`のYAML（binding）と、`.overlay`のノードで作る
- ドライバが動かないときは、`devicetree error`と、`zephyr.dts`の`status`、`compatible`を確認する

次回は、Zephyrの起動処理とマルチスレッドを学ぶ。<br><br>
