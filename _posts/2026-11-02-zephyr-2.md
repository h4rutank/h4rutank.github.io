## 1. Kconfigとは
KconfigはLinuxカーネルと同じ設定システムで、ソースコードを変えずにビルド時にカーネルやサブシステムの構成を変えるための仕組みである（参考: [Configuration System (Kconfig)](https://docs.zephyrproject.org/4.4.2/build/kconfig/index.html)）。<br>
- 設定項目（**シンボル**）は`Kconfig`ファイルで定義する。シンボル間の**依存関係**や、どの組み合わせが有効かを記述する
- Kconfigの出力は、`.config`と`autoconf.h`の2種類
<br><br>

Zephyrの開発を行っていると、同じくコンフィギュレーション用ファイルのDevicetreeと混同してしまう。KconfigとDevicetreeの違いを以下の表にまとめた。（参考: [Devicetree versus Kconfig](https://docs.zephyrproject.org/4.4.2/build/dts/dt-vs-kconfig.html)）<br>

| | Kconfig | Devicetree |
|-|-|-|
| 対象 | ソフトの機能（ログ、GPIOドライバを入れるか） | ハードの構成（UARTのアドレス、LEDのピン） |
| ファイル | `prj.conf`、`boards/<ボード名>.conf`、`Kconfig` | `.dts`、`.overlay` |
| ビルド後の最終結果 | `build\primary\zephyr\.config` | `build\primary\zephyr\zephyr.dts` |

一言でいうと、**Devicetreeはハードウェアとその起動時の設定を書いて、Kconfigはビルドに入れるソフトウェアの機能を決める**。<br>
たとえば、ボードにUARTがあるという事実はDevicetreeのノードで書く。そのUARTのドライバをビルドに入れるかどうかはKconfigで決める。<br><br>

ちなみに、ZephyrのKconfigとDevicetreeは組み込みLinuxのカーネル開発のそれと同じ役割です。（参考: [Kconfig Language](https://www.kernel.org/doc/html/latest/kbuild/kconfig-language.html)）<br><br>

### 1.1. 開発の流れ
Kconfigを使うと、**ソースコードを書き換えずに**機能の設定を変更できる。<br>
たとえば、ログ機能を入れるかどうかや、ログをどのレベルまで出力するかを設定したいときに使う。<br><br>

実際の開発は、次の5つの手順で行う。<br>
この記事では、手順1～4をZephyr本体が定義済みのログ機能（`CONFIG_LOG`）を例に、CC2340R5上で確かめる。<br>
手順5はアプリ専用のシンボル`CONFIG_TOTO`を例にする。<br>

| 手順 | やること | 参照先 | 節 |
|-|-|-|-|
| 1 | 設定したい機能のシンボルを探し、型・既定値・依存関係を調べる | menuconfig、公式のKconfig検索 | 2.1 |
| 2 | 設定値を書く | `prj.conf`など | 2.2 |
| 3 | ビルドして、効いたかを確認する | `.config`、ビルドログ | 2.3 |
| 4 | Cのコードで、設定に応じて処理を切り替える | `IS_ENABLED(CONFIG_...)`など | 2.3 |
| 5 | 必要なら、アプリ専用のシンボルを作る | `Kconfig`ファイル | 2.4 |

<br><br>

### 1.2. デバッグでの調べ方
設定したつもりなのに、動作が変わらないことがある。そのときは、以下のように調べていく。<br>
ビルドのログ出力・生成物から原因の候補を絞っていくことができる。<br>

| 手順 | 調べること | 参照先 | 節 |
|-|-|-|-|
| 1 | ビルドが成功したか。警告が出ていないか | ビルドログの`warning:` | 3.1 |
| 2 | 設定が、最終的にどの値になったか | `.config` | 2.3 |
| 3 | どのファイルの値が、後から上書きしたか | ビルドログの`Merged configuration`の行 | 2.2 |
| 4 | シンボルの依存関係を満たしているか | menuconfigの`/`と`?` | 2.1、3.1 |
| 5 | ドライバの場合、Devicetreeの`status`と、ドライバを使う宣言（`CONFIG_ADC`など）が揃っているか | `.config`の`DT_HAS_..._ENABLED`、`zephyr.dts` | 3.2 |

<br><br>

## 2. Kconfig開発手順
1.1節の5つの手順を、順に説明する。<br>

### 2.1. シンボルによる機能の有効化
Kconfigでは、機能のオン・オフや設定値を**シンボル**という単位で扱う。<br>
たとえば、ログ機能を入れるかどうかは`CONFIG_LOG`、ログの出力レベルは`CONFIG_LOG_DEFAULT_LEVEL`というシンボルで表される。<br><br>

Zephyrは、多くの機能がKconfigのシンボルで切り替えられるようになっていて、機能の数だけシンボルがある。<br>
`prj.conf`などの設定ファイルには、このシンボルを記述する。<br>
ただし、機能ごとの適切なシンボルをZephyr公式から検索して、次の3つを調べる必要がある。<br>

- 正しいシンボルの名前
- 設定できる値の種類と範囲、何も書かないときの既定値
- そのシンボルを有効にするために必要な条件（ほかのシンボルとの依存関係）

<br><br>
この3つを次の手順で調べる。<br>

#### 1) シンボルの名前を探す
最初はシンボルの名前が分からない。<br>
たとえば、「ログの出力レベルを変えたい」ときは、機能に関係する英語のキーワード（`log`、`level`など）を手がかりにして、次のどれかで探す。<br>

- **公式のKconfig検索**: [Kconfig検索](https://docs.zephyrproject.org/4.4.2/kconfig.html)のページに、キーワードを入力して、候補のシンボルを調べる
- **menuconfig**: `west build -t menuconfig`で開き、`/`を押して、名前の一部（たとえば`LOG_DEFAULT`）を入力する。該当するシンボルに、カーソルが移動する
- **ソースコードの検索**: VS Codeの全文検索（`Ctrl+Shift+F`）で、`C:\zephyr-ws\deps\zephyr`の`Kconfig*`ファイルを対象に、`config LOG_DEFAULT`を検索する。`subsys\logging\Kconfig.filtering`の37行目に、`config LOG_DEFAULT_LEVEL`が見つかる

こうして、シンボル`LOG_DEFAULT_LEVEL`を見つけ出す。<br>

#### 2) 定義を読む
見つかったシンボルの定義を読む。`LOG_DEFAULT_LEVEL`の定義は、次のとおりである。<br>

```text
config LOG_DEFAULT_LEVEL
	int "Default log level"
	default 3
	range 0 4
	help
	  Sets log level for modules which don't specify it explicitly. When
	  set to 0 it means log will not be activated for those modules.
	  Levels are:

	  - 0 OFF, do not write by default
	  - 1 ERROR, default to only write LOG_LEVEL_ERR
	  - 2 WARNING, default to write LOG_LEVEL_WRN
	  - 3 INFO, default to write LOG_LEVEL_INFO
	  - 4 DEBUG, default to write LOG_LEVEL_DBG
```
{: data-file="deps/zephyr/subsys/logging/Kconfig.filtering"}

この定義から、次のことが分かる。<br>

| 行 | 分かること |
|-|-|
| `config LOG_DEFAULT_LEVEL` | シンボルの名前。`CONFIG_`を付けて、設定ファイルやCのコードで使う（`CONFIG_LOG_DEFAULT_LEVEL`） |
| `int "Default log level"` | 型は整数。`"..."`の文字列は**プロンプト**で、menuconfigに出る説明になる |
| `default 3` | 何も設定しなければ3（情報レベル）になる |
| `range 0 4` | 設定できる値は、0から4まで |
| `help` | 値の意味。0=出力しない、1=エラー、2=警告、3=情報、4=デバッグ |

つまり、`prj.conf`に`CONFIG_LOG_DEFAULT_LEVEL=4`と書けば、デバッグレベルまで出力できる。範囲の外（たとえば5）を書くと、ビルドが止まる。<br>
menuconfigで`?`を押すと、これらの情報（説明と依存関係）を見られる。<br>
プロンプトを持つシンボル（visible）だけが、設定ファイルで値を設定できる。プロンプトのないシンボル（invisible）に値を書いても、無視される（[Setting Kconfig configuration values](https://docs.zephyrproject.org/4.4.2/build/kconfig/setting.html)）。<br>

#### 3) 依存関係をたどる
定義に`depends on`がある場合は、その条件を満たさないと、シンボルは有効にならない。<br>
例として、DMAを使ったUARTのドライバ（`UART_CC23X0_DMA_DRIVEN`）を有効にしたい場合を調べる。定義は、次のとおりである。<br>

```text
config UART_CC23X0_DMA_DRIVEN
	bool "DMA support for TI CC23X0 UART devices"
	depends on UART_CC23X0
	depends on UART_ASYNC_API
	select DMA
	help
	  DMA driven mode offloads data transfer tasks from the CPU.
```
{: data-file="deps/zephyr/drivers/serial/Kconfig.cc23x0"}

この定義から、次のことが分かる。<br>

| 行 | 分かること | 確認すること |
|-|-|-|
| `depends on UART_CC23X0` | CC23x0のUARTドライバが、有効である必要がある | `hello_world`の`.config`に、`CONFIG_UART_CC23X0=y`があるか？ |
| `depends on UART_ASYNC_API` | 非同期UART APIが、有効である必要がある | `prj.conf`に何も書かないと有効化されない |
| `select DMA` | `UART_CC23X0_DMA_DRIVEN`が有効になると、`DMA`も自動で有効化 | 設定は不要 |


次に、`UART_ASYNC_API`の定義は以下の通りである。<br>

```text
config UART_ASYNC_API
	bool "Asynchronous UART API"
	depends on SERIAL_SUPPORT_ASYNC
	help
	  This option enables asynchronous UART API.
```
{: data-file="deps/zephyr/drivers/serial/Kconfig"}

依存する`SERIAL_SUPPORT_ASYNC`は、`UART_CC23X0`の`select`で既に有効化されている。<br>
以上を踏まえて、`prj.conf`に次の2行を追記してビルドする。<br>

```text
CONFIG_UART_ASYNC_API=y
CONFIG_UART_CC23X0_DMA_DRIVEN=y
```
{: data-file="kconfig_hello/prj.conf"}

`.config`には、2つとも`=y`で出力され、`CONFIG_DMA=y`も有効化されている。<br><br>

### 2.2. 機能のコンフィギュレーション
Kconfigでは、機能の有効化・無効化だけでなく、機能のパラメータ設定を行える。<br>
パラメータは`CONFIG_シンボル名=値`のように記述する。<br>
`=`の前後に空白を入れないよう注意してください。<br>
アプリの設定は、`prj.conf`に書く。たとえば、ログ機能（`CONFIG_LOG`）の出力レベルを3（情報）にする場合は、以下のように記述する。<br>

```text
CONFIG_LOG=y
CONFIG_LOG_DEFAULT_LEVEL=3
```
{: data-file="kconfig_hello/prj.conf"}

<br>

このパラメータ設定は、シンボルと同じように複数のファイルに記述できる。<br>
CMakeのスクリプトは、KConfigのファイルを次の順に読み込んで、**後から読んだ値が、前の値を上書きする**。<br>

1. ボードの`lp_em_cc2340r5_defconfig`（`deps\zephyr\boards\ti\lp_em_cc2340r5\`にある既定値）
1. アプリの`prj.conf`
1. アプリの`boards\lp_em_cc2340r5.conf`（このボード専用の設定）
1. `EXTRA_CONF_FILE`で指定した追加ファイル


たとえば、`boards\lp_em_cc2340r5.conf`に`CONFIG_LOG_DEFAULT_LEVEL=4`と書いて、`prj.conf`の`CONFIG_LOG_DEFAULT_LEVEL=3`を上書きしてビルドしたら、`.config`では`CONFIG_LOG_DEFAULT_LEVEL=4`になった。<br>

使い分けは、アプリとして必要な機能は`prj.conf`、そのボードのときだけ変えたい値は`boards\ボード名.conf`、ビルドの種類ごとの差分は`EXTRA_CONF_FILE`である。<br><br>

### 2.3. 生成ファイルを確認して、アプリケーションで使う
ビルドすると、設定の結果が2つのファイルに出力される。<br>

- `.config`: そのビルドで最終的に使われた設定の一覧（`build\primary\zephyr\.config`）。最終的なシンボルの値を確認する
- `autoconf.h`: 設定をCのマクロにしたヘッダ（`build\primary\zephyr\include\generated\zephyr\autoconf.h`）

`hello_world`のビルドで作られた`autoconf.h`には、次の行がある。<br>

```c
#define CONFIG_SERIAL 1
#define CONFIG_SRAM_SIZE 36
#define CONFIG_BOARD_TARGET "lp_em_cc2340r5/cc2340r5"
```
{: data-file="autoconf.h"}

<br><br>

マクロが定義されている値をログ機能（`CONFIG_LOG`）で出力してみる。アプリケーションの`main.c`を書き換える。<br>

```c
#include <zephyr/kernel.h>

int main(void)
{
	printk("Hello World from Zephyr! %s\n", CONFIG_BOARD_TARGET);

#if defined(CONFIG_LOG)
	printk("CONFIG_LOG is enabled (level=%d)\n", CONFIG_LOG_DEFAULT_LEVEL);
#else
	printk("CONFIG_LOG is disabled\n");
#endif

	if (IS_ENABLED(CONFIG_LOG)) {
		printk("IS_ENABLED(CONFIG_LOG) = 1\n");
	} else {
		printk("IS_ENABLED(CONFIG_LOG) = 0\n");
	}

	return 0;
}
```
{: data-file="kconfig_hello/src/main.c"}

`IS_ENABLED()`は、有効なら1、無効なら0になるマクロで、`#ifdef`のようなものです。<br>

<img src="/img/1102_1.png" width="80%" height="auto"><br>

`prj.conf`の2行の設定（2.2節）の先頭に`#`を付けて無効にすると、表示が`CONFIG_LOG is disabled`に変わり、`.config`は`# CONFIG_LOG is not set`になる。<br>
`boards\lp_em_cc2340r5.conf`で出力レベルを4にした場合は、Tera Termに`CONFIG_LOG is enabled (level=4)`と表示される。レベル4（デバッグ）では、カーネルのデバッグログ（`dbg`と表示される行）も出力される。<br><br>



### 2.4. アプリ専用のシンボルを作る
Zephyr本体にないアプリ専用の設定項目は、アプリ直下の`Kconfig`ファイルで定義する。<br>
ここでは、[Zephyr RTOS Cookbook](https://www.oreilly.com/library/view/zephyr-rtos-cookbook/9781807429171/)を参考にして、意味のないダミーのシンボル`CONFIG_TOTO`を作る。<br>
アプリ専用のシンボルの作り方は、公式ドキュメントの[Application Development](https://docs.zephyrproject.org/4.4.2/develop/application/index.html#application-cmakelists-txt)（アプリ直下に`Kconfig`ファイルを作る手順と、ひな形）と、[Kconfig - Tips and Best Practices](https://docs.zephyrproject.org/4.4.2/build/kconfig/tips.html)（シンボルの書き方の指針）にある。<br>

```text
mainmenu "My ToTo App Configuration"

source "Kconfig.zephyr"

menu "ToTo Application Options"

config TOTO
	bool "Enable ToTo feature"
	default n
	help
	  Enables the toto dummy feature in this application.

endmenu
```
{: data-file="kconfig_toto/Kconfig"}

`mainmenu`はmenuconfigの画面の一番上に出るタイトル、`menu`から`endmenu`はメニューのまとまりである。<br>
**`source "Kconfig.zephyr"`は必須**で、Zephyr本体の`Kconfig`（この1行を含む）の代わりに、ユーザー定義の`Kconfig`からZephyr本体のソースを読み込むよう設定する（参考: [kconfig.cmake](https://github.com/zephyrproject-rtos/zephyr/blob/v4.4.2/cmake/modules/kconfig.cmake)）。<br><br>

アプリの`Kconfig`で定義したシンボルは、default設定で無効化されているので、追加の設定ファイル`toto.conf`を作成して`CONFIG_TOTO=y`と書く。読み込み先を指定するために、`CMakeLists.txt`で`EXTRA_CONF_FILE`を記述する。<br>

```text
CONFIG_TOTO=y
```
{: data-file="kconfig_toto/toto.conf"}

```cmake
cmake_minimum_required(VERSION 3.20.0)
set(EXTRA_CONF_FILE ${CMAKE_CURRENT_SOURCE_DIR}/toto.conf)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(kconfig_toto)
target_sources(app PRIVATE src/main.c)
```
{: data-file="kconfig_toto/CMakeLists.txt"}

**`set(EXTRA_CONF_FILE ...)`は、`find_package(Zephyr ...)`の前に書く**。設定の読み込みが、`find_package`の行で始まるからである。<br>
この行を`project(...)`の後ろへ移すと、ビルドは成功するが、設定が効かない。`.config`は`# CONFIG_TOTO is not set`のままで、ビルドログにも警告は出なかった。<br>
Cのコードでは、2.3節と同じように使える。次のコードで、`CONFIG_TOTO`が有効になったことを確認できる。<br>

```c
#include <zephyr/kernel.h>

int main(void)
{
	printk("Hello World from Zephyr!\n");

	if (IS_ENABLED(CONFIG_TOTO)) {
		printk("CONFIG_TOTO is enabled\n");
	}
	return 0;
}
```
{: data-file="kconfig_toto/src/main.c"}

## 3. Kconfigのエラー
### 3.1. ビルドエラー
ビルドが止まるときは、ログに`Aborting due to Kconfig warnings`と表示される。<br>
存在しないシンボルや、`range`の外の値を書くと、ビルドが止まる。<br>
一方、依存関係が満たされない場合は、警告が出るだけで、ビルドは続く。<br>

また、ビルドが成功しても、設定が効いていないことがある。<br>
最終的に有効化されたシンボルは、ビルドログの`warning:`と`.config`で確認する。<br>

| 症状 | 原因 |
|-|-|
| **ビルドが止まる** | 存在しないシンボルを書いた |
| **ビルドが止まる** | `range`の外の値を書いた |
| 警告だけで**ビルドは続く**が、設定は`n`になる | 依存関係が満たされない`=y`を書いた |

<br><br>

### 3.2. ドライバが有効化されない
ADCなどのドライバは、次の2つが揃うと有効になる。<br>

- ハードウェアが使用可能（Devicetreeで`status = "okay"`）
- ソフト機能を有効化（`CONFIG_ADC=y`）

どちらかが欠けると、ドライバがビルドに入らず`adc_read()`などが使えない。<br><br>
次の3種類のシンボルで、その条件を確認できる。<br>

|  | 確認すること | シンボル | 参照先 |
|-|-|-|-|
| 1 | ハードが使える状態か | `CONFIG_DT_HAS_TI_CC23X0_ADC_ENABLED` | Devicetree（ボードの`.dts`、`.overlay`） |
| 2 | ドライバを使うと宣言したか | `CONFIG_ADC` | `prj.conf` |
| 3 | CC23x0用のドライバ本体が有効か | `CONFIG_ADC_CC23X0` | 1と2が揃うと、自動で有効になる |

実際に`.config`を確認してみる。`prj.conf`に何も書かない場合は、1だけが`=y`で、2は`# CONFIG_ADC is not set`、3は項目自体がなかった。<br>
`prj.conf`に`CONFIG_ADC=y`を書くと、1から3がすべて`=y`になった。<br><br>

## Summary
Kconfigの開発手順とデバッグ方法を学んだ。<br>

- 既存のシンボルは、Kconfig検索やmenuconfigで探す。型、既定値、範囲、依存関係を読み、設定できるのはプロンプトを持つシンボルだけである
- 設定値は、`prj.conf`に`CONFIG_シンボル名=値`と書く。ボードの`defconfig`、`prj.conf`、`boards/ボード名.conf`、`EXTRA_CONF_FILE`の順に重なり、後に読まれる値が優先
- 最終的なコンフィギュレーションは、`.config`で確認する
- アプリ専用のシンボルは、アプリ直下の`Kconfig`で定義する
- 存在しないシンボルや範囲外の値を書くと、ビルドが止まる。依存関係を満たさない`=y`は、警告だけで`n`になるので、`.config`で確認する
